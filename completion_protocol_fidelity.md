## Previously Mismatched/Lost Properties

### 1. Accept Header
- **Browser**: `accept: */*`
- **Previous Proxy**: `accept: text/event-stream`
- **Issue**: Proxy was setting SSE-specific accept header, but browser uses generic `*/*`
- **Fix**: Changed `headers.set("accept", "text/event-stream")` to `headers.set("accept", "*/*")` in `buildCompletionHeaders()`
- **Location**: `src/deepseek_api/headers.ts:98`

### 2. Client Locale
- **Browser**: `x-client-locale: en_US`
- **Previous Proxy**: `x-client-locale: en_GB`
- **Issue**: Hardcoded locale constant did not match browser's US English
- **Fix**: Changed `DEEPSEEK.CLIENT.LOCALE` from `"en_GB"` to `"en_US"`
- **Location**: `src/deepseek_api/constants.ts:18`

## Browser-Only Transport Headers (Intentionally Not Reproduced)

The following headers are automatically generated by Chromium's network stack and are browser-specific transport metadata. They cannot and should not be replicated by a Cloudflare Workers server-side fetch:

| Header | Reason for Exclusion |
|--------|---------------------|
| `sec-ch-ua` | Browser UA client hint - server doesn't need to identify as Chrome |
| `sec-ch-ua-mobile` | Browser UA client hint - server is not mobile |
| `sec-ch-ua-platform` | Browser UA client hint - server platform differs from browser OS |
| `sec-fetch-dest` | Fetch metadata for browser security checks |
| `sec-fetch-mode` | Fetch metadata for browser CORS handling |
| `sec-fetch-site` | Fetch metadata for browser same-origin checks |
| `priority` | HTTP/2 stream prioritization hint from browser |

These headers serve browser security and transport optimization purposes. A server-side proxy making backend API calls does not require them.

## Session ID Difference (Explicitly Deferred)

| Aspect | Browser | Proxy | Status |
|--------|---------|-------|--------|
| Source of ID | URL parameter (client-generated at chat creation) | Server response from `/api/v0/chat_session/create` | DIFFERENT |
| Usage in completion | `chat_session_id: <url-derived-id>` | `chat_session_id: <server-returned-id>` | DIFFERENT |
| Functional outcome | Works | Works | ✅ BOTH WORK |

**Rationale for Deferral**: 
- The HAR proves the browser uses a different ID than the server returns
- However, the current proxy implementation using the server-returned ID works correctly (HTTP 200, successful SSE streams)
- DeepSeek's backend likely accepts both ID schemes or internally maps them
- Changing this would require implementing a client-side ID generation mechanism without clear evidence it's necessary
- This mission focuses on protocol fidelity for fields we can definitively match

## Conclusion

The proxy's DeepSeek completion wire protocol now matches the browser request field-for-field and header-for-header for all application-level properties that can be reproduced in a server-side context. The two identified mismatches (`accept` header and `x-client-locale`) have been corrected. Browser-specific transport headers are intentionally excluded as they serve client-side security/transport purposes irrelevant to server-to-server communication.

The session ID source difference remains but is functionally irrelevant since both approaches work with DeepSeek's backend.
